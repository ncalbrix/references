Chapter 1 : Data Engineering Described

Rôles du DE selon la maturité de l'utilisation de data dans l'entreprise (data maturity model) : 
    - Débutant de la donnée (starting with data) :
        - Contexte : 
            - Entreprise avec des buts peu/pas définis, une archi et une infra de donnée à un stade précoce
            - Le DE est souvent multi-casquette à ce stade, il peut aussi être DA, DS, Software Eng
            - Possible volonté de se plonger direct dans le ML : souvent mauvaise idée, les projets stagnent sans
            une bonne archi de données et une bonne compréhensions des données dispo et des buts recherchés

        - Objectifs du DE :
            - Avoir le soutien de key stakeholders pour des décisions critiques (design d'archi, priorités, etc)
            - Définir la bonnne archi de données
            - Comprendre et auditer la donnée utile
            - Créer la "culture de la donnée" de la boîte pour les futurs DA et DS, et générer les reportings
            ad-hoc en attendant

        - Conseils :
            - Créer des quick wins pour gagner la confiance des patron, mais garder en tête que les quick wins
            génèrent de la dette technique, avoir un plan pour la réduire
            - Ne pas travailler seul dans son coin : parler avec les autres équipes pour s'assurer de créer ou
            implémenter des outils utiles que les autres utiliseront
            - Utiliser le plus possible des solutions clefs en main
            - Créer des solutions custom uniquement si elles fournissent des avantages compétitifs

    - Intermédiaire de la donnée (scaling with data) :
        - Contexte : 
            - L'entreprise commence à avoir des process de données formels, et de moins en moins de besoins ad-hoc
            - Le DE n'est plus généraliste mais devient spécialiste se focalisant sur un ou des aspects particuliers
            du Data Engineering Lifecycle
            - L'objectif est maintenant de créer une architecture de données scalable

        - Objectifs du DE : 
            - Établir des process formels autour de la donnée
            - Créer des archi de données robustes et scalable
            - Adopter des pratique DevOps et DataOps
            - Construire des systèmes pour le ML
            - Customiser uniquement quand ça apporte un avantage compétitif (ex : système de recalcul de segments chez Nulberly)

        - Conseils :
            - Ne pas tomber dans le piège d'adopter des technos toutes nouvelles buzzwords
            - Utiliser des solution simples à déployer et à maintenir pour que l'équipe DE soit efficace
            - Communiquer autour de l'utilité de la data, avoir un rôle de formation autour de l'usage de la data

    - Leader de la donnée (leading with data) :
        - Contexte : 
            - L'entreprise est désormais DATA-DRIVEN
            - Les pipelines de données mises en place permettent aux équipes de faire du self-service analytics
            - L'intégration de nouvelles sources de données est fluide
            - Le DE implémente des systèmes de contrôle et des pratiques assurant la disponibilité de la donnée

        - Objectifs du DE :
            - Automatiser l'intégration de nouvelles sources de données
            - Créer des outils custom pour avoir un avantage compétitif business
            - Se focaliser sur des tâches de maintenance de la donnée et de DataOps
            - Déployer des outils permettant l'accès à la data à travers toute l'entreprise
            - Collaborer avec les Software Eng, ML eng, DA, etc; et créer une communauté technique pour la collaboration
            des équipes

        - Conseils : 
            - Éviter la complaisance afin de ne pas créer de la dette technique, se focaliser sur la maintenance
            et l'amélioration
            - Éviter les projets hobby inutiles, les distractions tech


Les langages que doit maîtriser un DE : 
    - SQL (ainsi que les formalismes modernes pour traiter les objets JSON et les données nested)
    - Python
    - Langage JVM, Java ou Scala principalement
    - bash

    - Secondairement, il est utile d'avoir des notions parmi les langages suivant : JavaScript, R, Go, Rust, C/C++, C#, Julia


Chapter 2 : The Data Engineering Lifecycle

Le data engineering lifecycle (DEL): framework du livre pour décrire les différentes étapes depuis les données brutes jusqu'au
produit fini à destination des DA, DS, MLE, clients et autres.
Il est divisé en 5 étapes : 
    - Generation
    - Storage
    - Ingestion
    - Transformation
    - Serving Data

Le DEL a un certain nombre de thèmes sous-jacents : sécurité, data management, DataOps, data architecture, orchestration,
software engineering.
En application, le DEL n'est pas forcément une suite bien organisée de ces étapes : certaines étapes peuvent se répéter, ou se
produire plusieurs fois. Notamment, l'étape de Storage se produit en fait tout au long du DEL.


Étapes du DEL

Étape de Generation : 
    - Systèmes source : systèmes à l'origine des données brutes utilisées dans le DEL (appareil ou essaim IoT, message queue,
      API, DB, etc.)
      Le DE doit comprendre le fonctionnement des systèmes sources avec lesquels il intéragit : leur façon de générer de la
      donnée, la fréquence et vitesse de génération, la variété des données générées.
      Le DE doit aussi avoir une ligne de communication avec les owners des systèmes sources, afin de prévoir les changements
      qui peuvent survenir dans ces systèmes (changement de formalisme, de type de champ, ou même de backend DB)
      Challenge du DE : travailler avec un nombre de systèmes sources variés, être organisé pour bien les connaître, leurs
      quirks etc.
      Le DE doit se poser un certain nombre de question concernant un système source pour bien le connaître (voir liste pages
      36-37, en annexe)

Étape de Storage :
    - La façon de stocker des données/la tech utilisée pour le faire a un grand impact sur la façon dont les données vont être
      utilisées, et de manière générale sur le reste du DEL, ceci car les systèmes de stockage ne sont jamais QUE des systèmes
      de stockage : les DB ont de grandes capacités de query et transformation, certains stockages d'objets supportent des
      queries (Amazon S3 Select), des frameworks de streaming (Kafka, Pulsar) peuvent faire de l'ingestion, du stockage, et
      supportent même des systèmes de query sur les messages qu'ils contiennent.
      De plus, au sein d'un même DEL, un système de stockage peut aussi être simultanément un système source.

    - Pour chaque type de donnée, le DE doit prendre en compte la fréquence d'accès à cette donnée (température) dans le choix
      du système de stockage : 
        - Hot Data : donnée requêtée plusieurs fois par jour, peut-être plusieurs fois par seconde (e.g. dans le cas de requêtes
        utilisateur sur un website). Nécessite un stockage rapide
        - Lukewarm Data : donnée requêtée toutes les semaines, ou tous les mois
        - Cold Data : donnée très peu requêtée, souvent données d'archive

    - Le DE doit se poser un certains nombre de questions sur la donnée afin de choisir un système de stockage approprié (voir
      liste pages 38-39, en annexe)

Étape d'Ingestion :
    - L'Ingestion désigne le ou les morceaux de software qui vont requêter les données et les écrire effectivement dans un
      système de stockage. Ils font le lien entre les systèmes sources et les systèmes de stockages. 
    - Les systèmes sources et les systèmes d'ingestion sont les plus gros bottlenecks du DEL. La plupart du temps, les systèmes
      sources sont en dehors de la responsabilité du DE (sauf système source interne), les systèmes d'ingestion doivent donc
      recevoir un soin tout particulier.

    - Questions à se poser en préparation du développement d'un système d'ingestion en annexe (page 40)

    - Batch vs. Streaming : 
        - Ingestion en streaming : arrivage continu de données, en temps réel ou presque-réel
        - Ingestion en batch : découpage de streaming en paquets de données. Le découpage peut être fait temporellement (un
          nouveau batch tous les X temps) ou en terme de volume (un nouveau batch tous les X événements/enregistrements etc.)
        - Le batch reste une option populaire et robuste, notamment pour l'analytics ou le ML, mais le développement de
          plateformes de streaming et de traitement d'événements rend le traitement continu de streams de données de plus en
          plus populaire.
          De manière générale, l'ingestion en streaming doit uniquement être implémentée dans les cas spécifiques où la containte
          temporelle est indispensable dans le système final, car le streaming vient avec un lot de coûts et de complexités.

        - Quelques questions à prendre en considération pour décider si une ingestion en stream est plus propice qu'une ingestion
          en batch en annexe (page 41)

    - Modèle push vs. modèle pull :
        - Modèle push : le système source va pousser de la donnée vers un endpoint, une message queue, ou autre, que le système
          d'ingestion va récupérer pour stocker. Dans ce modèle le système d'ingestion est plus "passif"/en écoute. Typiquement
          plus utilisé dans un contexte de streaming (e.g. un CDC continu où un système source publie un message dans une message
          queue à chaque fois qu'une ligne est changée dans une DB source)
        - Modèle pull : le système d'ingestion va requêter directement le système source pour récupérer la nouvelle donnée.
          Typiquement plus utilisé dans un contexte de batch (e.g. un process ETL)

Étape de Transformation : 
    - Ensemble de processus de modifications des données brutes provenant d'un système source pour les rendre lisibles, utiles et
      fiables.
      Dans le FDE, la Transformation est traitée comme une étape à part entière, alors qu'en pratique les transformations de
      données se produisent la plupart du temps à plusieurs moments du DEL.
      Par exemple : 
        - Transformations simples pendant l'ingestion (transtypages dans les bons types, formattage standard, suppression de
          données érronées)
        - Plus tard en base de données : transformation de schema de données, normalisation
        - Avant de servir un processus de ML : agrégations à grande échelle, featurization (la plupart du temps faites en tandem
          avec un DS)
    - À noter que les transformations "en vol" dans une pipeline de streaming deviennent de plus en plus populaires
    - La logique business ou métier est une source de transformations de données majeure. Dans ces cas, la modélisation de donnée
      doit être très claire avec des règles business établie pour en tirer le plus de valeur (e.g. les CSP ou catégories d'âge
      dans la donnée Sofinco)

Étape de Serving :
    - Étape du DEL où l'on va créer de la valeur à partir de la donnée recueillie. Créer de la valeur veut dire utiliser la
      donnée à une fin utile pour l'entreprise. Il faut garder à l'esprit qu'il faut éviter les "projets d'orgueil" : des projets
      dans lesquels la donnée finale n'est jamais utilisée (typiquement, des projets ou l'aspect technique est privilégié par
      rapport à l'apport final de la donnée).
    - Quelques applications pour lesquelles on doit servir de la donnée : analytics, ML, reverse ETL

    - Analytics :
        - Coeur de la plupart des projets data. Ici, découpée en 3 types d'analytics : BI, Opérationnelle, Intégrée

        - BI : type d'analytics qui utilise des données pour décrire l'état passé et présent d'un aspect business, voire pour
          émettre des prédictions. Se repose sur des règles business bien établies.
          Dans ce type d'analytics, on ne suit pas non plus forcément strictement les étapes du DEL, notamment au niveau de la
          définition des règles business : celle-ci peuvent être définies préalablement pendant l'étape de Transformation, ou au
          contraire laisser la donnée propre mais peu transformée et appliquer les règles business au moment du Serving pour une
          analyse BI.
          Un système BI peut gérer un répertoire de logiques et définitions business qui seront utilisées par les users pour
          requêter la donnée et créer des analyses. Ce genre de pratiques de self-service apparaît plutôt dans des entreprises
          à haut niveau de maturité data, et nécessitent une donnée de bonne qualité, ainsi qu'une bonne organisation.

        - Opérationnelle : type d'analytics qui se focalise sur un aspect terre à terre de l'entreprise (état de stocks, santé
          d'une app, traffic sur un site, etc.). Souvent de l'analyse en temps réel qui bénéficie de systèmes de streaming.
          Diffère du BI en le fait qu'elle se concentre sur des données actuelles et non historiques.

        - Intégrée : type d'analytics qui est réalisée directement par un client hors de l'entreprise, via un accès à la donnée
          (typiquement un SaaS). Pose un certain nombres de problématiques différentes des analyses BI internes : volume de
          requêtes, silotage des données, sécurisation des données et des accès, problématiques d'ownership, etc.

    - ML :
        - Dans ce domaine, les responsabilités des DE se recoupent beaucoup avec celles liées à l'analytics. Les frontières entre
          DE, MLE et analytics engineers peuvent être assez floues.
          Un outil spécifique au ML qui peut être déployé est le Feature Store, qui permets à différentes équipes ou projets de
          partager des features pour leurs modèles de ML, ainsi qu'avoir un historique de définitions de ces features
        - Un DE n'a pas besoin d'être expert en ML, avoir quelques bases est néanmoins très utile, ainsi que connaître les use
          cases des modèles de ML dans l'entreprise, et les responsabilités des différentes équipes d'analytics et DS; ceci afin
          de maintenir une communication et collaboration efficace.
        - Attention à ne pas se lancer dans des projets ML ambitieux trop tôt, il est toujours préférable d'avoir une solide
          plateforme et culture de données avant.

    - Reverse ETL :
        - C'est la pratique de prendre de la donnée ingérée et transformée (l'output du DEL), et la feed à nouveau dans un
          système source. Historiquement considérée comme un antipattern, cette pratique est de plus en plus utilisée, souvent
          avantageuse ou indispensable (e.g. utiliser les résultats d'une analyse, les scores calculés par un modèle, etc, et les
          stocker/utiliser dans un système de production ou un système SaaS pour un client externe).
        - Exemple en marketing : calculer des bids sur les line items en utilisant un modèle de ML, puis feed ces résultats dans
          une DSP style Google Ads.


Thèmes sous-jacent du DEL
    - Avec la maturité, la pratique du Data Engineering s'abstrait de plus en plus de la tech et englobe un certain nombre de
      pratiques et thèmes sous-jacents : Sécurité, Data Management, DataOps, Data Architecture, Orchestration, Software Engineering

    - Sécurité :
        - Les DE doivent comprendre la sécurité des données et des accès, et mettre en place le principe least privilege : donner
          accès à un utilisateur ou système uniquement aux données et ressources essentielles pour leurs tâches (par opposition au
          fait de donner des droits admin à tout le monde).
        - Créer/promouvoir une culture de sécurité informatique/d'accès à la donnée, en tandem avec une équipe de sécu si elle
          existe
        - Il faut aussi gérer la sécurité dans le temps (e.g. créer des rôles d'accès révocables automatiquement dans le temps
          pour accès à une donnée sensible)
        - Un DE doit comprendre le user management et l'identity and access management (IAM), un peu de sécurité réseau, politique
          de gestion des mdp. Sur cet aspect, le DE se rapproche un peu d'un administrateur système.

    - Data Management : 
        - Gros sujet très "enterprise", ensemble de politiques de gestion et d'éléments culturels liés à la donnée au sein d'une
          entreprise. Définition dans le Data Management Body of Knowledge : 
            "Data management is the development, execution, and supervision of plans, policies,
             programs, and practices that deliver, control, protect, and enhance the value of data
             and information assets throughout their lifecycle."
        - Le Data Management englobe un certain nombre d'aspects, qui incluent : 
            - La gouvernance des données (ainsi que la découvrabilité et la responsabilité de chaque donnée)
            - La modélisation et le design
            - Le Data Lineage
            - Le stockage et les opérations
            - L'intégration et l'interopérabilité
            - le Data Lifecycle Management
            - Les systèmes pour l'analytics avancée et le ML
            - L'éthique et la vie privée

        - La gouvernance de la donnée :
            - Ensemble de pratiques pour assurer la qualité, l'intégrité, la sécurité et l'utilisabilité des données. La
              gouvernance encourage les personnes, processus et systèmes à maximiser la valeur de la donnée au travers d'une
              entreprise, tout en la protégeant avec des contrôles de sécurité appropriés.
            - La gouvernance englobe les sujets centraux de découvrabilité, sécurité, et responsabilité.

            - Découvrabilité : 
                - Capacité d'un utilisateur final à avoir un accès rapide et fiable à la donnée dont il a besoin. Il doit pouvoir
                  savoir d'où la donnée vient, son lien avec d'autres données, et sa signification (+ accès simple à de la doc
                  pour un user technique : type des champs, schema, définitions, etc.)
                  Concepts clefs : gestion des métadonnées, Master Data Management

                - Gestion des métadonnées : 
                    - Métadonnées : données sur la donnée; soutien l'intégralité du DEL. C'est la donnée nécessaire pour rendre
                      la donnée générale découvrable et gouvernable.
                      Deux types : générées automatiquement, et générées par un acteur humain (sujet à erreurs).
                    - De plus en plus d'outils existent pour collecter et gérer les métadonnées : data catalogs, data-lineage
                      tracking systems, outils de gestion de métadonnées. Certains outils permettent de parcourir des DB pour
                      mettre en évidence les liens entre les données/tables, et surveiller des pipelines de données pour créer
                      automatiquement un lineage de la données (quelle donnée vient d'où, où elle va, par qui/quoi elle est
                      ensuite utilisée, etc.)
                    - Certains défi restent à prendre en compte : interopérabilité (e.g. connection d'un système de gestion de
                      métadonnées avec une DB) et standards.
                    - Aspect social des métadonnées : owners, consumers, experts de domaines
                    - 4 catégories de métadonnées utiles au DE : business, techniques, opérationnelles, de référence

                    - Métadonnées de business : 
                        - Contiennent les définitions, règles et logiques business (e.g. comment est défini un client? etc.)

                    - Métadonnées techniques :
                        - Donnée créée et utilisée par les systèmes du DEL (modèles, schema, lineage, champs et types, workflow
                          des pipelines)
                        - Métadonnées de pipeline : créées/capturées par des systèmes d'orchestration type Airflow (e.g. horaire
                          planifié, dépendances systèmes et de données, configurations, détails de connexion, etc.)
                        - Métadonnées de lineage : compile les origines, changements et dépendances d'une donnée dans le temps
                        - Métadonnées de schema : décrit la structure d'une données stockée sur un système (DB, Data Warehouse,
                          Data Lake, système de fichiers)

                    - Métadonnée opérationnelle :
                        - Décrivent les résultats et sorties opérationnelles de différents systèmes : statistiques sur les
                          processus, ID de jobs, données utilisées dans un process, logs de runtime, logs d'erreurs

                    - Métadonnée de référence :
                        - Donnée pour classer d'autres données/lookup tables (e.g. codes internes comme des codes de produits,
                          codes géographiques, unités de mesures, etc.)

            - Responsabilité :
                - Assigner à un individu (pas forcément DE) la gouvernance d'une donnée, qui coordonnera les efforts de
                  gouvernance entre les différents acteurs concernés
                - La responsabilité peut-être attribuée selon plusieurs niveau de granularité : par ex un individu responsable
                  d'une table ou d'un stream de logs, ou un individu responsable d'un champ spécifique (définition, évolution
                  dans le temps) utilisé au travers de plusieurs tables/systèmes.

            - Qualité :
                - La qualité d'une donnée représente la conformité de la donnée avec ce qu'on attend d'elle. La donnée doit
                  notamment être conforme aux métadonnées de business (définitions, logiques, etc.). Le DE doit s'assurrer de la
                  qualité de la donnée tout au long du DEL, notamment au travers de tests variés.
                - On peut définir la qualité de la donnée selon trois axes :
                    - Précision : la donnée est-elle factuellement correcte? y a-t-il des valeurs dupliquées? les valeurs
                      numériques sont-elles précises?
                    - Complétion : est-ce que les enregistrements sont complets? est-ce que tous les champs requis ont une valeur
                      valide?
                    - Ponctualité : est-ce que les enregistrements sont disponibles dans un temps raisonnable/quand on en a
                      besoin?
                - Chacun de ces axes est nuancé et n'a pas de solution technique définitive, la plupart du temps ils doivent
                  être abordés conjointement de façon humaine et avec des solutions techniques.
                - Exemples :
                    - Sur un website, le traffic généré par des robots est-il pertinent par rapport à ce que l'on essaie de
                      mesurer? Si non, il faut un moyen de flagger ce traffic afin de ne pas compromettre la précision de la
                      donnée globale
                    - Sur une app avec un fonctionnement hors-ligne, à quel moment définit-on qu'une donnée n'est plus ponctuelle?
                      Quels standards met-on en place pour la donnée non-ponctuelle, et comment les faire appliquer?

        - La modélisation et le design de données :
            - Pratique par laquelle on transforme une donnée brute vers une forme utilisable (à des fins d'analytics et de ML).
            - Traditionnellement une pratique de DB Administrator (DBA) ou développeur ETL, la modélisation et le design de
              données peut en fait intervenir à beaucoup d'endroit différent (ingénieur qui développe le format de logs d'un
              appareil IoT, webdev qui design la réponse JSON d'une API ou le schema d'une table SQL).
            - Pratique qui devient complexe avec la multiplication des types, formats et usages des données, néanmoins de plus
              en plus d'outils prennent ça en compte pour accroître la flexibilité du design tout en gardant des séparations
              logiques et hiérarchiques.
            - La modélisation est un sujet important malgré la difficulté qui vient avec la multiplicité des données, sans quoi
              on se retrouve rapidement avec de la donnée écrite et jamais utilisée (car inutilisable)
            - Exemple de grand chantier de modélisation de données : la normalisation des bases clients chez Numberly

        - Le Data Lineage :
            - (lit. la lignée des données, les ancêtres des données) Processus de tracking, pour une donnée, des systèmes qui
              l'ont traitée et des autres données dont elle dépend.
            - Aide beaucoup pour la recherche d'erreurs, la compréhension/répartition des responsabilités, et le debuggage.
            - Avoir un data lineage clair et efficace facillite notamment d'être en conformité avec différentes réglementations
              (RGPD, etc.) : si un utilisateur veut que l'on supprime les données qui le concernent, on peut facilement trouver
              d'où elles viennent afin de les supprimer/d'arrêter de les recueillir.

        - L'intégration et l'interopérabilité :
            - Fait d'intégrer les données au sein d'une multiplicité d'outils, de techs et de processus.
            - Sujet de plus en plus important à mesure que l'on travaille dans une environnement cloud et/ou hétérogène, où
              différents outils doivent traiter la donnée à la demande.
            - L'intégration se fait de plus en plus via des API tout-usage, plutôt qu'en utilisant des connecteurs DB dédiés
              (e.g. on pull d'un système source via son API, on stocke sur un S3, on utilise l'API Snowflake pour charger cette
              donnée dans une table, lancer une query, exporter les résultats, etc.)
            - Ceci fait que ces traitements d'intégrations peuvent se faire facilement avec des scripts Python et une lib
              d'appels http, mais la complexité va résider dans la multiplication de ces traitements et la complexité des
              pipelines qui en découlent. Pour gérer tout ça, on a besoin d'outils d'orchestration.

        - Data Lifecycle Management :
            - Gestion de la fin de vie des données.
            - Deux raisons principales : 
                - L'espace de stockage : soit il est limité on-premise, soit il est de plus en plus coûteux via un service cloud
                - Les règlements type RGPD qui oblige à supprimer des données après un certain temps, ou sur demande des
                  utilisateurs
            - La suppression de données de façon granulaire est le plus souvent simple dans un Data Warehouse sur le cloud, via
              des clauses WHERE en SQL.
            - Sur des technologies moins flexibles (e.g. Hive), il existe souvent des outils pour gérer facilement la suppression
              de lignes en DB (e.g. Hive ACID)

        - Éthique et vie privée :
            - Responsabilité du DE (entre autre) de promouvoir une culture de la donnée mettant la vie privée au coeur des
              différentes considérations. Les DE doivent faire cet effort conscient malgré le fait que ce soit un sujet souvent
              négligé.
            - Notamment : faire en sorte qu'aucune information personnellement identifiable (PII) ne soit sauvegardée; faire en
              sorte d'éviter le plus possible l'appartition de biais (racistes, sociaux, etc.) dans les jeux de données (en
              conjonction avec les DS).

    - DataOps :
        - Fait correspondre les best practices de méthodes Agile, DevOps et Statistical Process Control (SPC) aux produits
          data.
        - Selon Data Kitchen :
            DataOps is a collection of technical practices, workflows, cultural norms, and architec‐
            tural patterns that enable:
                • Rapid innovation and experimentation delivering new insights to customers with
                increasing velocity
                • Extremely high data quality and very low error rates
                • Collaboration across complex arrays of people, technology, and environments
                • Clear measurement, monitoring, and transparency of results

        - En premier lieu, les DataOps sont un ensemble de pratiques culturelles et politiques au sein d'une entreprise :
          cycles de communication et collaboration avec le métier, amélioration continue, itérations rapide.
        - L'implémentation de pratiques de DataOps peut varier selon le niveau de maturité data d'une entreprise : dans une
          entreprise peu mature, les DataOps peuvent être implémentées dès les premières heures des projets pour faire partie
          intégrente de la culture des process de l'entreprise; pour une entreprise déjà mature mais qui manque de DataOps, 
          le DE peut commencer à implémenter ces pratiques dans les workflows petit à petit, en commençant par de
          l'observabilité et du monitoring (e.g. mail auto pour prévenir de jobs qui ont crash, ou bot sur un channel
          slack/mattermost).
        - Quel que soit le niveau de maturité de l'entreprise, le DE doit être au courant des aspects culturels et techniques
          des DataOps
        - Les DataOps peuvent être séparés en trois composantes techniques : l'automatisation, l'observabilité et monitoring,
          et la réponse sur incident

        - Automatisation :
            - Explicite. Similaire au DevOps dans les pratiques, i.e. change management (contrôle de version des
              environements, du code, de la donnée), intégration continue/déploiement continu (CI/CD), et configuration
              as code.
            - Exemple sur 3 étapes de maturité :
                - Peu mature : jobs cron hébergés sur le cloud, peu/pas de logs ou de messages d'erreurs, pas de gestion
                  de dépendance entre jobs (un job cron se finit trop tard, un autre downstream a donc commencé et va
                  crash ou utiliser des données périmées)
                - Assez mature : mise en place d'un framework d'orchestration type Airflow ou Dagster, les jobs cron sont
                  migrés vers des DAG Airflow, les dépendances entre DAG sont gérées par le framework, les jobs peuvent
                  être lancés plus rapidement car automatiquement après leurs dépendances
                - Très mature : un DS déploie un DAG buggé, qui fait crash le webserver Airflow. L'équipe DE empêche donc
                  le déploiement manuel de DAGs et implémente des tests automatiques et des processus de monitoring pour
                  s'assurer que chaque nouveau DAG se déploie correctement.
            - Les DE peuvent aussi développer du custom code/framework pour des aspects précis, e.g. de la gestion de
              metadonnées ou de lineage

        - Observabilité et Monitoring :
            - Va consister en un certain nombre de processus de monitoring et d'alerting (logs, mail, bots de chats,
              notifications) et de traçage (stacktrace, lineage de jobs en erreur).
            - Les conséquences de l'absence de processus d'observabilités peuvent être catastrophiques : utilisation de
              données périmées/erronées pour faire des décisions business ou entraîner des modèles qui à leur tour
              produiront des prédictions peu fiables. À terme, ça peut complètement fragiliser la confiance des
              dirigeants envers les équipes data.
            - Voir la méthode DODD (Data Observability Driven Development), analogue du TDD (Test Driven Development),
              même si en pratique je pense que c'est difficile à implémenter comme type de design.

        - Réponse sur incident :
            - Utilisation des capacités d'automatisation et d'observabilité pour régler le plus rapidement les problèmes qui
              peuvent survenir (système ou job qui crash, modèle de ML qui périme, schema qui change et met un reporting en
              erreur) ainsi qu'identifier leurs causes.
            - Sujet qui qui englobe aussi bien les techs et outils, que la communication libre et sans accusations, aussi bien
              au sein de l'équipe DE qu'au travers de toute l'entreprise.
            - Les DE doivent proactivement chercher les problèmes qui peuvent survenir afin que les utilisateurs n'aient pas à le
              faire, et pour ne pas rompre leur confiance

    - Data Architecture :
        - Désigne l'état actuel et futur des systèmes de données mis à profit pour servir les besoins et stratégies en terme de
          données de l'entreprise.
        - Un DE doit d'abord comprendre les besoins business, les prérequis de ces besoins, et traduire ces prérequis en
          solutions techniques afin de collecter et servir de la données. Il doit donc connaître les avantages et inconvénients
          des techs, outils, patterns qu'il met en place ou utilise.
        - Le DE n'est pas un Data Architect, mais il doit travailler en tandem avec, utiliser les design du Data Architect et
          donner des feedbacks dessus.

    - Orchestration :
        - Processus de coordination de jobs afin que ceux-ci puissent tourner aussi vite et efficacement que possible selon une
          une cadence automatisée. Les moteurs/frameworks d'orchestration intègrent des métadonnées sur les dépendances entre
          tâches et entre jobs sous la forme de Graphes Dirigés Acycliques (DAG).
        - Un système d'orchestration doit être constamment en ligne et disponibles, afin de faire tourner tous les jobs qui lui
          sont intégrés, ainsi que faire remonter des erreurs lorsque des jobs crashent, des dépendances ne sont pas remplies,
          par mail aux équipes DE ou via d'autres canaux.
        - Principal moteur d'orchestration : Airflow
        - D'autres moteurs intéressants voient le jour : Prefect, Dagster (essaient d'améliorer la portabilité et la testabilité
          des DAGs pour gérer facilement les silotages d'environnement de dev et de prod etc.), Argo (construit autour de
          Kubernetes), Metaflow (orienté ML).
        - L'orchestration est un concept purement batch.

    - Software Engineering :
        - Le software engineering est toujours une compétence clef qu'un DE doit avoir. Avec le temps, le développement d'outils
          et de framework tend à abstraire de plus en plus les détails bas-niveau de programmation dans les projets liés à la
          donnée (e.g. omniprésence de SQL dans les environnements cloud). Néanmoins les capacités en software engineering
          restent critiques dans le data engineering, par exemple dans ces quelques domaines du DEL :

        - Core Data Processing Code :
            - Code central qui gère le traitement des données, apparaît tout au long du DEL (ingestion, transformation, serving).
              Le DE doit être compétent avec SQL, et des langages ou frameworks comme Spark ou Beam. Le DE doit aussi comprendre
              et mettre en place des tests (unitaires, de régression, d'intégration, end-to-end, et smoke)

        - Développement Open Source :
            - Beaucoup de DE adoptent des frameworks open-source et peuvent alors y contribuer pour améliorer certains aspects.
            - Il faut garder en tête de faire de la veille pour vérifier si il n'existe pas déjà un outil qui résout le problème
              qu'un DE cherche à résoudre.
            - Il faut aussi peser le coût de développement et d'ownership d'un outil.

        - Streaming :
            - Le streaming est un processus plus compliqué que le batch de façon inhérente, et l'écosystème autour est moins
              mature; cela donne lieu à des problèmes de programmations plus complexes.
            - Par exemple : les opérations classiques dont on a l'habitude comme les jointures doivent être repensées.
            - Le DE doit pouvoir écrire du code pour appliquer des fonctions de fenêtrages sur des streams, afin de calculer par
              exemple des statistiques en temps réel sur des streams (e.g. une moyenne sur les n derniers évènements).

        - Infrastructure as Code (IaC) :
            - Application du software engineering à la configuration et la gestion d'infrastructure. Les DE doivent savoir
              utiliser les frameworks IaC afin de gérer leur infrastructure dans un environnement cloud, plutôt que de lancer ou
              éteindre des instances ou installer du software manuellement. Ces frameworks sont le plus souvent dépendants d'une
              plateforme cloud en particulier.
            - La notion d'IaC peut être appliquée à des containers (Docker) et à Kubernetes, avec des outils comme Helm.
            - Ces pratiques sont une partie vitale du DevOps et permettent la répétabilité et le contrôle de version pour les
              déploiements.

        - Pipelines as Code :
            - Concept clef des systèmes d'orchestration, c'est le fait de déclarer des jobs, tâches, et dépendances entre elles
              et eux, sous forme de code, le plus souvent Python (e.g. le code pour programmer un DAG Airflow).

        - Résolution de problèmes tous-usages :
            - Le DE rencontrera des cas limites ou des problèmes qui ne sont pas pris en compte par les outils, libs ou
              frameworks qu'il utilise. Il doit être capable d'écrire du code custom (plus ou moins bas niveau) afin de pouvoir
              prendre en compte ces cas.
            - Il doit aussi être à l'aise avec la manipulation d'API, la récolte et transformation de données et formats, la
              gestion d'exceptions, le design de fonctions, classes et libs, etc.


Chapter 3 : Designing Good Data Architecture

Qu'est-ce que la Data Architecture?

    - Il faut d'abord définir l'Enterprise Architecture
        - Contient plusieurs sous-ensembles : Business Architecture, Technical Architecture, Application Architecture, Data
          Architecture
        - L'Enterprise Architecture peut-être définie comme la conception de systèmes qui supportent le changement au sein d'une
          entreprise, accompli en utilisant des décisions flexibles et réversibles, qui sont prise en faisant une évaluation
          rigoureuse des compromis.
        - Concepts clefs : décisions flexibles et réversibles, gestion des changements, évaluation des compromis (trade-offs)

        - Les décisions flexibles et réversibles sont des décisions business, technologiques ou autre qui offrent facilement un
          chemin retour. Elles sont indispensables dans un écosystème ou les pratiques, les technologies et les trends changent
          rapidement. Adopter une culture de décisions réversibles permet aussi à une entreprise de ne pas se figer dans un
          modèle spécifique qui pourrait devenir périmé, et de pouvoir s'adapter rapidement.
        - La gestion des changements représente la façon concrète dont sont incarnées les décisions flexibles et réversibles :
          comment mettre en oeuvre une décision? selon quels processus? Souvent, on aura tendance à séparer une décision en un
          nombre de petites étapes, elles-mêmes réversible (e.g. l'adoption d'une nouvelle DB au sein d'un service).
        - L'évaluation des compromis est assez explicite. Chaque décision concernant un système numérique vient avec son lot de
          contraintes et possibles compromis, qu'ils soient physiques (e.g. latence, fiabilité, densité, concommation d'énergie)
          ou non (e.g. caractéristiques de langages ou frameworks, complexité, budget).

        - Point central de l'Enterprise Architecture : faire l'équilibre entre la flexibilité et les compromis.

    - La Data Architecture est donc un sous-ensemble de l'Enterprise Architecture, contenant les mêmes concepts clefs, appliqué
      à la donnée :
        Conception de systèmes qui supportent les besoin en données changeants d'une entreprise, qui sont atteints par
        l'application de décisions flexibles et réversibles après évaluation rigoureuse des compromis.
    - Ça s'incarne dans le Data Engineering au niveau des systèmes et frameworks qui constituent les éléments clefs du DEL (dans
      FDE, désigné comme Data Engineering Architecture, et utilisé de façon interchangeable avec Data Architecture).
    - Aspects internes de la Data Architecture : Operational Architecture et Technical Architecture
        - Operational Architecture : le quoi, qu'est-ce qui doit être fait? Décisions et objectifs business
        - Technical Architecture : le comment ce doit être fait? Composants techniques, frameworks, design patterns


La "Bonne" Data Architecture

    - Les concepts clefs derrière la "bonne" Data Architecture est qu'elle doit être au service du business, répondre aux besoins
      business le mieux possible, et qu'elle doit être composée de blocs communs à plusieurs besoins business, flexibles et
      facilement réustilisables.
    - Par opposition, une mauvaise Data Architecture peut être monolithique, utiliser un outil par principe et non pas parce
      qu'il répond efficacement à un besoin ou une contrainte, et a souvent ses composants fortement couplés.
    - Une caractéristique importante d'une bonne Data Architecture est qu'elle est flexible, et qu'elle peut être changée à bas
      coût (humain, financier).


Principes d'une bonne Data Architecture

    - Voir deux frameworks de Data Architecture :
        - AWS Well-Architected Framework
        - Google Cloud's Five Principles for Cloud-Native Architecture

    - Dans FDE, les auteurs listent 9 principes fondamentaux de Data Architecture :
        - Choisir les composants partagés avec soin
        - Planifier en prenant en compte les échecs
        - Architecturer pour scale
        - L'Architecture est du leadership
        - Toujours architecturer
        - Construire des systèmes faiblement couplés
        - Faire des décisions réversibles
        - Prioriser la sécurité
        - Adopter la FinOps

    - Principe 1 : Choisir les composants partagés avec soin
        - Un DE doit pouvoir choisir des composants et des pratiques partagées (entre les sytèmes et entre les persones) qui
          puissent être utilisés partout au travers d'une entreprise, et qui facilitent la collaboration entre équipes.
        - Ces composants peuvent être n'importe quoi qui peut être appliqué largement au sein de l'entreprise : systèmes d'object
          storage, système de contrôle de version, d'observabilité, de monitoring, d'orchestration, moteurs de traitement.
        - Les composants partagés doivent avoir des capacités de gestion des permissions et des accès.
        - Pour choisir un composant partagé, il faut équilibrer entre l'utilité pour des projets individuels, faciliter la
          collaboration et l'interopérabilité, tout en ne forçant pas les équipes à utiliser un outil tous-usages qui ne
          répondrait pas bien à leurs besoins.

    - Principe 2 : Planifier en prenant en compte les échecs
        - Le hardware, aussi bon soit-il, viendra toujours à avoir des pannes. Il faut donc évaluer en avance les scénarios de
          pannes selon différents critères :
            - Disponibilité : le proportion de temps qu'un service ou composant passe dans un état opérationnel
            - Fiabilité : probabilité qu'un système satisfasse les standards définis durant un intervalle de temps donné
            - Objectif de Temps de Rétablissement (Recovery Time Objective - RTO) : temps maximum acceptable d'une panne pour un
              système ou service donné, défini selon l'impact business de ladite panne (différence d'importance entre un système
              interne et un système accessible par un client par ex.)
            - Objectif d'État de Rétablissement : état acceptable d'un système ou service après un rétablissement (en data,
              concerne principalement le volume maximal acceptable de données perdues)
        - Le DE doit prendre en compte ces critères au moment de prendre un décision d'architecture

    - Principe 3 : Architecturer pour scale
        - La scalabilité va dans deux sens :
            - Scale Up, c'est à dire ajouter des instances d'un système, par exemple des nodes dans un cluster Hadoop pour
              entraîner un modèle sur une énorme quantité de données, ou ajouter des instances dans un système d'ingestion en
              streaming pour accommoder un pic d'arrivée de données.
            - Scale Down, c'est à dire retirer (automatiquement) des instances d'un système une fois un besoin intense passé,
              ceci afin de réduire les coûts (notamment dans un contexte cloud) ou libérer des ressources matérielles.
        - Un système élastique peut scale up et down dynamiquement en réponse à une charge de traitement, idéalement de façon
          automatique.
        - Certains systèmes peuvent scale to zero, c'est à dire s'éteindre complètement lorsqu'ils ne sont pas utilisés (e.g.
          serverless functions, serverless online analytical processing (OLAP) DB).
        - Il faut prendre en compte que le scaling apporte une couche de complexité non-négligeable, il peut être judicieux
          selon le use case d'avoir une architecture fixe en terme de volume pour plus de simplicité (e.g. une DB avec un
          serveur de secours pour une petite app web interne)

    - Principe 4 : L'Architecture est du leadership
        - Un bon Data Architect doit avoir à la fois de grandes capacités techniques et de grandes capacités de leadership. Il
          doit pourvoir prendre des décisions techniques précises et informées, et déléguer le plus gros du travail de détail aux
          DE.
        - Le Data Architect ne doit pas occuper une posture de surplomb et être la seule partie prenante dans les décisions
          d'architecture. À l'inverse, il doit consulter les équipes techniques et le business afin de prendre les décisions les
          plus informées possibles et qui répondent le mieux aux besoins et contraintes de tous.
        - Le Data Architect doit jouer un rôle de mentor dans les équipes data, faire de la formation et élever le niveau
          technique afin de donner la possibilité à tous d'avoir une meilleure vision sur les meilleures décisions techniques à
          prendre et la manière de répondre aux besoin techniques.
        - En tant que DE, il faut le plus possible chercher le mentorat d'un Data Architect, ainsi que contribuer à et répandre
          la culture data produite par les Data Architect.

    - Principe 5 : Toujours architecturer
        - Un Data Architect ne doit pas se contenter de maintenir l'architecture data actuelle d'une entreprise, mais à l'inverse
          doit avoir une architecture cible en tête, toujours selon les besoins business et les changements dans le paysage tech,
          à laquelle il doit faire tendre l'architecture actuelle à travers un plan séquencé de petites étapes.
        - L'architecture cible changera vraisemblablement dans le temps avec les besoins business et avancées technologiques, et
          le plan séquencé servira à prioriser les changements les plus urgents.

    - Principe 6 : Construire des systèmes faiblement couplés
        - Les systèmes faiblement couplés possède les caractéristiques suivantes :
            - Un système est séparé en plusieurs petits composants
            - Les composants communiquent entre eux via une interface/couche d'abstraction (API, messaging bus) qui cache les
              détails de fonctionnement de chaque composant (backend DB, classes, appels de méthodes, etc.)
            - En conséquence, les changements internes d'un composant ne doivent pas avoir d'impact sur les autres composants :
              les détails de programmation et de fonctionnement sont cachés derrière une API stable.
            - Finalement, il n'y a donc pas de cycle de release global de tout le système : chaque composant est mis à jour
              séparément au fur et à mesure que des changements et améliorations sont faits.
        - Ces principes peuvent être appliqués à l'organisation elle-même pour obtenir des équipes faiblement couplées qui se
          chargent individuellement d'un composant, indépendemment des autres équipes. Chaque équipe peut alors publier l'API
          du composant dont elle se charge afin que les autres équipes l'utilisent, et chaque équipe peut faire des requêtes de
          nouvelles features aux autres.

    - Principe 7 : Faire des décisions réversibles
        - Étant donné le rythme de changement de l'écosystème data, le Data Architect doit prendre le plus possible de décisions
          réversibles, dans ses choix de pratiques, de frameworks, de technologies.
        - Il doit aussi être préparé à mettre à jour ou adopter de meilleures techs ou pratiques à mesure que l'écosystème
          évolue.

    - Principe 8 : Prioriser la sécurité
        - Le DE doit assumer la responsabilité de la sécurité des systèmes qu'il construit et maintient.
        - Deux idées principales : la zero-trust security, et le shared responsibility security model

        - Zero-trust Security :
            - Type de modèle dans lequel l'entreprise définit un réseau avec des acteurs de confiance à l'intérieur et des
              acteurs auxquels on ne fait pas confiance à l'extérieur (e.g. une salle de serveur sans accès depuis l'extérieur
              mais qui donne accès à tout une fois à l'intérieur). Ce modèle est particulièrement vulnérable aux attaques depuis
              l'intérieur (phishing, qui permet de trouver un accès intérieur à des services internes, etc).
            - Dans un contexte cloud, la notion de frontière entre l'extérieur et l'intérieur devient d'autant plus floue.
        - Shared Responsibility Model :
            - Modèle s'appliquant aux environnement cloud, dans lequel le fournisseur cloud est resposable de la sécurité du
              cloud en lui même, de son infra, etc., et l'utilisateur du cloud (l'entreprise) est responsable de la sécurité de
              son utilisation du cloud (données stockées, types d'accès, régulation en vigueur type RGPD, etc)

        - Dans une entreprise, il y a souvent la présence d'une équipe de sécurité dédiée qui sera en charge de mettre en place
          et faire appliquer les politiques de sécurité. Les environnements cloud déplacent ces responsabilités (au moins en
          partie) vers les DE qui ne sont pas explicitement des ingé de sécurité. Le DE doit donc assumer ces responsabilités
          implicites.

    - Principe 9 : Adopter la FinOps
        - FinOps : ensemble de pratiques à la croisée entre le DevOps et la Finance afin de gérer efficacement et dynamiquement
          les dépenses en infra cloud dans le but de maximiser le profit tiré de ces infras.
        - Dans un setting on-premise, les systèmes de données sont acquis ponctuellement en faisant une dépense de capital à
          chaque fois
            - Si on dépense trop : puissance de calcul non-utilisée, argent gâché
            - Si on dépense pas assez : ralentissement des projets data, plus de temps alloué au contrôle de la charge sur
              l'infra, besoins en upgrade plus réguliers et donc plus de temps alloué aux upgrades
        - Dans un setting cloud, variations de modèle de paiement à l'utilisation (paiement par query, paiement par temps de
          calcul, paiement par capacité de calcul, etc). Approche plus efficace la plupart du temps, mais qui demande de gérer
          les budgets et priorités efficacement
        - La FinOps allie les questions budgétaires et techniques (e.g. quelle est la meilleure approche pour faire tourner
          efficacement et à bas coût un job quotidien conséquent? quel mix d'instances Spot AWS utiliser (instances de
          serveurs qui ne sont utilisées par personne, à très bas coût mais pas disponible de façon fiable)?)
        - La FinOps transforme la gestion du budget et le monitoring des coûts d'un processus régulier en un processus continu,
          ainsi une entreprise peut choisir de mettre en place des politiques de plafonds de dépenses indépassables, couplées
          avec un mode d'échec acceptable pour l'utilisateur (ceci peut notamment permettre de se prémunir de surcoûts
          considérables lors d'attaques DDoS)


Principaux concepts d'architecture

    - Domaines et Services :
        - Domaine : Domaine thématique dans le monde réel pour lequel on créé une architecture
        - Service : Ensemble de fonctionnalité dont le but est d'accomplir une tâche précise (e.g. un service de traitement de
          commande ne va faire QUE traiter les commandes, pas gérer l'inventaire ou mettre à jour les profils client)
        - Un domaine peut contenir plusieurs services (e.g. un domaine "vente" peut contenir les services "commandes", "devis" et
          "produits")
        - Plusieurs domaines peuvent partager des services (e.g. les domaines "vente" et "comptabilité" partagent un service
          "devis" car les ventes génèrent des devis, et la comptabilité doit suivre les devis afin de s'assurer que les paiements
          sont faits). Les équipes en question (e.g. vente et comptabilité) ont la responsabilité de leur propre domaine.
        - Quand le DE conçoit un domaine, il doit partir du réel, voir ce que ce domaine représente dans le réel, et travailler
          depuis ce constat.
        - Il faut éviter de calquer l'achitecture d'un domaine sur un modèle général ou ce qui est fait dans une autre
          entreprise, et plutôt travailler directement avec les utilisateurs et les parties prenantes afin de construire les
          systèmes spécifiques qui les aideront dans leurs tâches. Éviter de construire un système sans consulter personne, et
          que personne ne finira par utiliser.

    - Systèmes distribués, scalabilité, concevoir pour l'échec
        - En tant que DE, on s'intéresse à quatre caractéristiques des systèmes de données :
            - Scalabilité : permet d'accroître (ou réduire) la capacité de traitement d'un système
            - Élasticité : capacité d'un système à scale up ou down dynamiquement selon sa charge actuelle
            - Disponibilité : pourcentage de temps pendant lequel un système ou service est dans un état utilisable
            - Fiabilité : probabilité qu'un système réponde aux standards de fonctionnement définis, durant un intervalle de
              temps spécifié
        - Ces différentes caractéristiques sont liées :
            - Un système qui ne répond pas aux standards de fonctionnement durant un intervalle de temps spécifié peut arrêter de
              fonctionner, ainsi une faible fiabilité peut donner lieu à une faible disponibilité
            - À l'inverse, une scalabilité dynamique permet de s'assurer de la performance d'un système sans intervention
              manuelle, ainsi une bonne élasticité améliore la fiabilité d'un système
        - La scalabilité peut s'incarner de différentes façons :
            - Scaling vertical : ajouter de la puissance de calcul à une machine (plus de ram, de place de stockage, un meilleur
              CPU). Méthode de scaling sensible aux pannes, besoin de backups, etc. Généralement, une machine seule, même si
              très performante, ne peut pas fournir une haute disponibilité et fiabilité.
            - Scaling horizontal : ajouter des machines, à travers un système distribué. En majorité du temps, ce genre de
              système est organisé avec un noeud leader et des noeuds travailleurs.
                - Le noeud leader est le point de contact pour l'instanciation, le suivi du progrès et de la complétions des
                  charges de travail.
                - Quand un job est lancé, le noeud leader s'occupe de distribuer les tâches entre les noeuds travailleurs, qui
                  vont les compléter et retourner les résultats au noeud leader
                - La majorité des systèmes distribués incluent aussi de la redondance : la donnée est répliquée entre les noeuds
                  pour que, si une machine meurt, d'autres puissent reprendre la tâche là où elle a été arrêtée.
        - Les systèmes distribués sont maintenant très répandus dans les technologies data, et abstraient les mécanismes internes
          bas niveau. Il est néanmoins très recommandé pour un DE se renseigner sur les fonctionnements généraux de ces systèmes
          pour améliorer la performances des pipelines.

    - Couplage fort vs. couplage faible : Tiers, Monolithes, et Microservices
        - À la conception d'une architecture, le DE choisit le niveau d'interdépendance entre les domaines, services et
          ressources.
        - Couplage fort : chaque domaine et service est dépendant de chaque autre domaine et service
        - Couplage faible : chaque domaine et service est décentralisé et n'a pas de dépendance stricte avec aucun autre domaine
          et service.
        - Dans un scénario de couplage faible, il est facile pour des équipes décentralisées qui ne se parlent pas de concevoir
          des systèmes avec des données inutilisables par les autres équipes, il faut donc mettre en place des standards communs,
          assigner la propriété et la responsabilité des systèmes et données aux personnes en charge de leurs domaines et
          services respectifs (un bon data management en somme).

        - Tiers d'architecture
            - Une architecture possède différentes couches (couche de données, d'appplication, de logique métier, de
              présentation). Le DE doit savoir comment découpler ces couches, comment les structurer pour assurer une bonne
              fiabilité et flexibilité.

            - Architecture à un tiers
                - L'application et la DB sont fortement couplées, et résident sur la même machine (e.g. un laptop, une VM sur le
                  cloud). Si le serveur, la DB ou l'application plantent, toute l'architecture tombe.
                - Un certain nombre de limitations : par exemple, si on essaie de faire de l'analytics sur une DB d'application
                  de prod, celle-ci risque de devenir surchargée et va rendre l'application indisponible.
                - À utiliser uniquement pour du prototypage

            - Architecture multi-tiers
                - Répond aux problèmes posés par une architecture à un tiers en découplant les différentes couches (données,
                  application, logique métier, présentation, etc). Ces couches sont organisées de façon hiérarchiques : les
                  couches les plus hautes sont dépendantes des couches les plus basses, qui elles ne dépandent pas nécessairement
                  des couches les plus hautes.
                - La notion importante est de séparer les données, l'application, et la présentation.
                - Type d'achitecture multi-tiers répandu : l'architecture en 3 tiers, très utilisée dans les applications
                  client - serveur. Elle possède donc trois couche : la couche de données tout en bas, la couche d'application au
                  dessus, puis la couche de présentation encore au dessus. Le choix de la tech pour chaque couche peut donc être
                  fait indépendamment des autres

            - Dans une architecture multi-tiers, le DE doit considérer à la fois comment séparer les différentes couches, et
              comment sont partagées les ressources au sein de chaque couche lorsqu'on travaille dans un environnement distribué.
              Est-ce qu'on veut éviter les conflits pour accéder à des ressources entre les noeuds? On peut alors mettre en place
              une Shared-Nothing Architecture, dans laquelle chaque noeud se charge d'une requête, et ne partage pas la ram, la
              mémoire disque ou le CPU avec les autres noeuds.
              Est-ce qu'on veut que chaque noeud puisse gérer plusieurs requête? On court le risque de conflit de ressources
              entre les noeuds. On peut se dire que la ram et mémoire disque sera accessible par tous les noeuds : c'est une
              Shared Disk Architecture, répandue pour se prémunir des plantages de noeuds individuels.

        - Monolithes
            - Notion générale : inclure le plus de choses possibles au même endroit
            - Version extrême : une seule codebase, qui tourne sur une seule machine, et qui fournit à la fois la logique
              d'application et l'interface utilisateur
            - Deux axes de couplage :
                - Couplage technologique : se réfère aux tiers de l'architecture, sont-ils séparés ou non
                - Couplage de domaines : est-ce que plusieurs domaines sont regroupés ou non
            - On peut avoir par exemple un monolithe architecturé en plusieurs tiers découplés mais qui mélange plusieurs
              domaines, ou un monolithe avec une architecture à un tiers réduit à un seul domaine.
            - Le fort couplage d'un monolithe sous-entend un manque de modularité de ses composants. Cela rend la mise à jour ou
              l'amélioration d'un composant d'un monolithe particulièrement ardue, et celle-ci pourra provoquer des conséquences
              innatendues dans d'autres composants.
            - Un monolithe se forme souvent lorsqu'une équipe data ou software ignore la complexité grandissante d'un système, et
              y ajoute du code sans considération architecturale.

        - Microservices
            - À l'opposé complet d'un monolithe. Architecture en microservices : ensemble de services séparés, décentralisés,
              faiblement couplés. Chaque service remplit une fonction spécifique. Si un service est en échec, cela n'a pas
              d'impact sur le fonctionnement des autres.
            - Question centrale : comment transformer un monolithe en microservices? Dépend de la complexité du monolithe et du
              niveau d'effort requis d'en extraire des services. Il est possible que le monolithe ne puisse pas être séparé du
              tout, dans ce cas il est plus simple de créer une architecture en microservices parallèle, de zéro.
              Question tech autant que question organisationnelle : il faut l'aval des parties prenantes du monolithe pour
              commencer à le séparer en services.

        - Considérations de Data Architecture
            - Les architectures de données fortement couplées sont toujours assez communes, ceci est dû à la nature des techs de
              données existante et la façon dont elles s'intègrent les unes aux autres.
            - Exemple : des pipelines qui ingèrent des données depuis différentes sources et qui les intègrent dans un seul Data
              Warehouse : le Data Warehouse est monolithique. Un changement qui peut-être fait serait d'avoir plusieurs Data
              Warehouses pour différents domaines (ventes, inventaire, produit). Cela peut néanmoins ajouter une couche de
              complexité non négligeable au niveau de l'analytics, qui se base souvent sur plusieurs domaines en même temps.
            - Le DE doit rester flexible : ne pas être dogmatique sur l'usage de microservices, mais prôner le plus possible du
              couplage faible, prendre en compte les limitations des techs data, et faire des choix de techs facilement
              réversibles qui permettent de la modularité.
            - Il faut garder à l'esprit le problème organisationnel du couplage des domaines.
              Est-ce qu'on utilise une approche centralisée : une équipe collecte la donnée pour tous les domaines et s'occupe de
              la rendre utilisable par toute l'entreprise? Approche classique du Data Warehousing, comme à Numberly, à ceci près
              que différents DE avaient la resposabilité de différents clients
              À l'inverse, est-ce qu'on sépare la resposabilité de l'ingestion et de la préparation des données entre chaque
              équipe selon leur domaine? (Pattern du Data Mesh)
            - Les monolithes ne sont pas mauvais pas essence, ils peuvent être pratiques pour avoir rapidement une solution
              fonctionnelle, néanmoins il faut garder en tête un moyen de le séparer en services plus faiblement couplés à
              l'avenir.

    - Accès utilisateurs : Single tenant vs. Multinenant
        - Un DE doit souvent prendre des décisions sur le partage ou non de systèmes ou données entre plusieurs équipes,
          organisations, ou clients.
        - Les services de calcul cloud sont multitenant par nature, mais l'usage de VM permet un degré de séparation entre les
          utilisateurs. L'Object Storage est multitenant, mais le fournisseur cloud garantit la sécurité et l'isolation tant que
          le client configure correctement les accès.
        - À plus basse échelle, le DE doit prendre des décisions sur la multitenancy, par exemple : dans une grosse entreprise,
          est-ce que plusieurs départements partagent le même data warehouse? Est-ce qu'une table contient des données de
          plusieurs clients? (penser à la normalisation chez Numberly, notamment pour les données de tag)
        - Deux facteurs principaux dans la multitenancy : performances et sécurité.
            - Performances : est-ce que l'usage intensif d'un tenant causera des dégradations de performances pour un autre
              tenant?
            - Sécurité : les données entre tenant sont-elles bien isolées? Exemple : si on a des données de plusieurs clients
              dans une seule table, on peut offrir un accès via une vue qui isole les données par client. Il faut comprendre
              clairement le fonctionnement de la tech utilisée pour s'assurer de la sécurité de nos actions.

    - Architecture Event-Driven
        - Type d'architecture centrée sur le concept d'event : une action qui se produit, qui change l'état de quelque chose
          (e.g. un nouveau client est acquis, un client fait une nouvelle commande, ou met à jour une de ses commandes, etc)
        - Un workflow event-driven englobe la capacité de créer, mettre à jour, et propager de façon asynchrone les events entre
          différentes partie du DEL.
        - Workflow séparé en trois domaines principaux : production d'event, routing d'event, et consommation d'event. Il faut
          que le producteur, le router et le consommateur de l'event soit découplés (le plus possible).
        - Avantage de ce type d'architecture : l'état d'un event peut être distribué à plusieurs service en même temps
          (toujours de façon asynchrone). Utile pour se prémunir d'un service qui plante ou d'un noeud mis en échec dans un
          système distribué, ainsi que pour que plusieurs consommateurs ou services aient accès au même event.

    - Projets Brownfield vs. projets Greenfield
        - Projets Brownfield :
            - Impliquent de refactorer et réorganiser une architecture existante. Contraintes nées des choix passés et présents
              (en terme de tech et d'organisation).
            - Projets qui requièrent une compréhension profonde de l'architecture existante, et des interactions entre des
              vieilles ou moins vieilles techs.
            - Il faut le plus possible connaître le contexte dans lequel les décisions passées ont été prises afin de les
              comprendre, diagnostiquer les problèmes, identifier les opportunités et les possibles écueils.
            - Il faudra déprécier les anciennes techs ou architectures à un moment, plusieurs approches pour cela :
                - Changement complet tout à la fois : donne souvent lieux à des décisions irréversibles et coûteuses, à éviter
                - Strangler Fig Pattern : des nouveaux systèmes sont conçus progressivement remplaçants un à un les composants de
                  l'ancienne architecture. Permet de prendre des décisions réversibles et de jauger plus précisemment l'impact de
                  la dépréciation de systèmes dépendants les uns des autres.
            - La dépréciation de composants ou systèmes n'est pas toujours possible (e.g. une équipe a toujours besoin critique
              d'un vieux système). Quand la dépréciation est possible, il faut faire de la politique et de la com pour montrer
              l'avantage des nouveaux systèmes.

        - Projets Greenfield
            - Projets où l'on commence de zéro, ou l'on conçoit une architecture du début.
            - Souvent plus simples que les projets Brownfield
            - Il faut faire attention à ne pas tomber dans le piège d'adopter des techs uniquement parce qu'elles sont cools,
              alors qu'elles ne seront peut-être pas forcément utiles ou alors trop complexes pour les besoins métier.
            - Toujours prioriser les besoins métier.


Exemples et Types de Data Architecture

    - Le Data Warehouse :
        - Plateforme centrale de donnée utilisée pour l'analytics, le reporting, l'entraînement ML, etc.
        - Contient des données hautement formatées et structurées.
        - Parmi les types d'architecture data les plus vieux et les mieux établis.
        - Dans le passé, réservé à des grosses entreprises avec beaucoup de moyens (gros coûts techniques et humains pour la mise
          en place et la maintenance). Avec les services cloud, c'est devenu un type d'architecture très accessible : les
          considérations d'infrastructure sont déléguées aux fournisseurs cloud.
        - 2 composantes d'achitecture de Data Warehouse notables : architecture organisationnelle et architecture techniques

        - Architecture Organisationnelle de Data Warehouse :
            - Organise les données associées à certains process et structures des équipes métiers
            - 2 grandes caractéristiques :

            - Séparer le traitement de l'analytics des DB de production
                - Indispensable pour réduire la charge des DB de prod et améliorer la performance de l'analytics

            - Centraliser et organiser la donnée
                - Typiquement, un Data Warehouse tire des données d'applications en utilisant de l'ETL.
                - Extract : tirer des données de systèmes sources
                - Transform : nettoyer, formater, normaliser les données et appliquer des règles métier
                - Load : écrire les données transformer dans le système de DB du Data Warehouse (souvent dans plusieurs Data
                  Marts, qui séparent les données selon différents business, clients, départements, etc)

        - Architecture Technique de Data Warehouse :
            - Systèmes MPP (Massively Parallel Processing, architecture de système distribué où les processeur ou nodes sont
              séparés et ont leur propre capacité de calcul et mémoire séparées des autres) sont devenus populaires dans les 80's
            - Optimisés pour la lecture en parallèle d'énormes quantités de données et permettre des agrégations et calculs
              statistiques très performants.

        - Variation de l'ETL : l'ELT
            - La donnée est lue et écrite telle quelle (ou presque) dans une zone de staging du Data Warehouse. L'étape de
              transformation est retardée et déléguée directement au Data Warehouse pour profiter de ses capacités de calcul
              distribué massives. Le Data Warehouse lui-même se chargera donc de lire la donnée de sa zone de staging, appliquer
              par batches des transformations, normalisations, etc, puis écrire la donnée transformée dans sa zone de destination
              en lui-même.
              Chez Numberly, Hive était le Data Warehouse.
            - L'ELT peut aussi être utilisé dans un contexte de streaming, par ex si des events sont streamés au sein d'un
              processus de CDC (Change Data Capture).

    - Le Data Warehouse Cloud :
        - Évolution significative par rapport à sa contrepartie On-Premise, et donc changement dans son architecture
          organisationnelle
        - Flexibilité : pas besoin de prévoir d'un coup le nombre de machines à avoir dans son cluster, on peut en ajouter au fur
          et à mesure. Possibilité d'ajouter et de supprimer des clusters selon des use cases spécifiques/des pics de charge de
          calcul.
        - Possibilité de stocker et traiter de grands volumes de texte brut par ligne en DB, ainsi que des documents JSON
          complexes.
        - Au fur et à mesure des évolutions, les Data Warehouse Cloud s'éloignent du concept de simple Data Warehouse pour
          devenir des plateformes de données plus vastes.
        - Acteur principaux : Amazon Redshift, Google BigQuery, Snowflake

    - Les Data Marts :
        - Sous-ensemble d'un Data Warehouse concentré sur une organisation/département/client, à visée d'analytics.
        - Chaque organisation/département/client a son propre Data Mart, avec des données spécifiques aux besoins de cette
          organisation.
        - Les Data Marts peuvent proposer des données qui ont subi une étape supplémentaire de transformation/jointure/agrégation
          afin d'être directement utilisables pour des reportings ou de l'analytics
        - Chez Numberly, les Data Marts étaient typiquement incarnées par les bases clients non-normalisées, ouvertes en écriture

    - Le Data Lake :
        - Architecture, le plus souvent cloud, permettant de stocker de grands volumes de données structurées et non-structurées
          grâce à de l'object storage, couplée à des capacités de calcul à la demande et un vaste choix de techs pour le
          requêtage et le calcul (MapReduce, Spark, Ray, Presto, Hive, etc)
        - Le Data Lake est venu avec son lot de promesse et de hype dans les années 2010, mais, à part pour certains cas réussis
          dans de grosses entreprises tech (e.g. Facebook, Netflix), il est souvent devenu source de grandes complexités, de
          frustrations, de mauvaises pratiques data et de données écrites et jamais utilisées (voir Data Swamp)
        - À l'origine, les Data Lake était en write-only, ce qui rendait particulièrement difficile la mise à jour de données, la
          suppression ciblée etc (passait la plupart du temps par l'écriture de nouvelles tables)

    - Convergence, Data Lakes nouvelle génération, et Data Platform
        - Différentes évolutions nées notamment des défauts du Data Lake
        - Databricks propose le Data Lakehouse : contrôle, gestion de données et structures de données du Data Warehouse, couplés
          avec de l'object storage supportant une multitude de moteurs de requêtes. Notamment, support des transactions ACID.
        - L'architecture des Data Warehouse cloud s'est rapprochée de l'archi de Data Lake, avec notamment la séparation du
          stockage et des capacités de calcul, le stockage de données non-structurées et semi-structurées, et l'intégration de
          techs comme Spark ou Beam.
        - Les fournisseurs cloud proposent désormais des Data Platform qui combinent les capacités du Data Warehouse et du Data
          Lake (AWS, Azure, Google Cloud, Snowflake, Databricks). Ils offrent un ensemble d'outils intégrés pour travailler avec
          tout type de données, depuis les données non-structurées jusqu'au DB relationnelles.
          Les DE devront choisir un fournisseur selon l'écosystème du fournisseur en question, le degré d'ouverture du software, etc.

    - La Modern Data Stack
        - Type d'architecture d'analytics mettant en avant l'utilisation de différents composants cloud standards et simple
          d'utilisation et d'installation pour créer un ensemble modulaire et cost-effective.
        - Types de composants : pipelines de données, stockage, gestion de données, monitoring, dataviz, exploration.
        - Les outils évoluent rapidement mais l'idée centrale reste la même : réduction de complexité et modularité
        - S'intègre bien avec la notion de Data Platform
        - Les résultats attendus sont notamment le self-service data (pipelines et analytics) et la gestion des données agile

    - Lambda Architecture
        - Type d'architecture né du besoin d'unifier une archi batch avec une archi streaming.
        - Plusieurs systèmes fonctionnant indépendamment les uns des autres : batch, streaming, et serving
        - Le système source envoie des données à deux destination : une streaming et une batch
        - Le système de streaming doit servir la donnée le plus rapidement possible dans une couche "speed", souvent une DB NoSQL
        - Dans la couche batch, les données sont transformées et stockées dans un système type Data Warehouse
        - La couche de serving unifie les deux couches précédentes en agrégeant les résultats des queries de ces deux couches
        - Défaut majeur : complexité. Plusieurs systèmes avec plusieurs codebases, difficile à maintenir, code et données
          difficile à réconcilier
        - Type d'architecture de moins en moins utilisé et peu recommandé

    - Kappa Architecture :
        - Type d'architecture né en réponse aux défauts de la Lambda Architecture
        - Basé sur le fait de supprimer la couche batch de la Lambda Architecture, et de traiter toutes les données (ingestion,
          stockage, serving) via une plateforme de traitement de stream type Kafka.
        - Les données peuvent être ainsi lues en temps réel via un stream, et peuvent être traitées en batch en rejouant une
          grande portion d'un stream.
        - La Kappa Architecture n'a pas été adoptée à grande échelle, car mettre en place une plateforme complète de traitement
          de streams reste complexe. De plus, dans la pratique, la Kappa Architecture est complexe et chère. Le batch "natif"
          reste une option bien plus simple et cost-effective pour traiter de gros jeux de données historiques.

    - Le modèle Dataflow et le Batch et Streaming Unifié
        - Les architectures Lambda et Kappa avaient pour but d'unifier le batch et le streaming, mais n'y sont pas arrivé. Elles
          ont néanmoins servi d'inspiration à des initiatives futures.
        - Concept central : unifier le code pour gérer les traitements batch et streaming.
        - Dans ce but, Google a développé le modèle Dataflow et le framework Apache Beam qui l'implémente.
        - Modèle Dataflow :
            - Toute donnée est un event
            - Les agrégations sont faites sur différents types de fenêtres
            - Les streams d'event en temps réel sont des données non-bornées
            - Les batches sont des streams de données bornées, les bornes fournissent ainsi une fenêtre
            - Différents types de fenêtres pour les agrégations en temps réel (fenêtre glissantes, fenêtres fixes (type group
              by))
            - Le traitement temps réel et par batch se fait dans le même système avec du code quasiment identique
        - La philosophie de considérer le batch comme cas particulier de streaming est de plus en plus adoptée
